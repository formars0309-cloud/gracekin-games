# 커뮤니티 회원 서버 배포 준비

이 문서는 새 전용 Fly 앱 `gracekin-games-community`의 배포 준비안이다. 현재 앱·Machine·볼륨·운영 비밀키를 새로 만들지 않았고, 아래 외부 작업 명령도 실행하지 않았다. 기존 경국지계 앱과 그 비밀키·볼륨은 사용하지 않는다. 계정·서버 코드의 변경 없이 대문, 게임 홈페이지, 커뮤니티 화면과 `/api`를 한 서버에서 제공한다.

## 검토할 자원과 설정

| 항목 | 준비한 값 | 이유 |
| --- | --- | --- |
| 전용 앱 | `gracekin-games-community` | 기존 게임 서버와 분리. 앱 이름 사용 가능 여부는 생성 직전에 확인 |
| 지역 | `nrt` | 도쿄 단일 지역 |
| Machine | `shared-cpu-1x`, 메모리 512MB, 1개 | 인증의 암호 연산을 고려한 초기안. 256MB보다 여유를 두었으며 실부하 측정값은 아님 |
| 영속 볼륨 | `community_data`, 1GB, `/data` | `/data/community.sqlite`와 SQLite 부속 파일 보존 |
| 유휴 상태 | 자동 정지·자동 시작, 최소 실행 0개 | 요청이 없으면 정지 가능. 다음 방문에 초기 응답 지연이 생길 수 있음 |
| 동시 요청 | 권장 한도 10, 최대 20 | 측정 전의 보수적인 초기값 |
| 상태 확인 | `GET /api/community/session`, 30초 간격·5초 제한·시작 유예 30초 | 익명 요청은 `200`과 `user: null`을 반환. 별도 `/health`는 없음 |
| 배포 | rolling, 한 번에 1개 중단 | SQLite 단일 서버라 배포 중 잠시 중단될 수 있음 |

위 자원에는 실행 시간, 볼륨, 전송량 등에 따른 비용이 발생한다. **신규 자원 비용은 사용자가 확인하고 진행한다.** 금액은 아직 확정하지 않았으며, 생성 전에 [공식 요금 계산기](https://fly.io/calculator/)에 지역·512MB·Machine 1개·1GB 볼륨과 예상 사용량을 넣어 확인한다.

자동 시작·정지, 동시 요청 한도와 상태 확인 헤더는 [Fly 설정 문서](https://docs.fly.io/reference/configuration)의 형식을 따른다. `--ha=false`로 최초 배포의 추가 Machine 생성을 막는다. 이 옵션은 Machine 수를 설정 파일만으로 고정해 주는 것은 아니므로 배포 후 실제 1개인지 확인한다. [Fly 배포 명령](https://docs.fly.io/flyctl/cmd/fly_deploy)

볼륨은 Machine 하나에 연결되며 여러 볼륨 사이에 자동 동기화되지 않는다. 이번 안은 SQLite 복제 기능을 추가하지 않아 두 번째 Machine을 띄우지 않는다. 단일 Machine·볼륨은 장애나 배포 때 중단될 수 있으므로 공개 운영 전 별도 백업과 복구 절차가 필요하다. 일일 스냅샷 5일 보관을 켜 두었지만 이것만을 유일한 백업으로 삼지 않는다. [Fly 볼륨 안내](https://docs.fly.io/volumes/overview/)

## 이미지와 비밀정보 경계

`Dockerfile`은 `node:24.20.0-bookworm-slim`으로 고정했다. 2026-10-15에 [공식 Docker Hub 태그 API](https://hub.docker.com/v2/repositories/library/node/tags/24.20.0-bookworm-slim)에서 활성 태그와 amd64·arm64·ppc64le 제공을 확인했다. 의존성은 잠금 파일로 `npm ci --omit=dev --ignore-scripts` 설치한다.

새 볼륨은 이미지의 `/data` 권한을 덮어쓰므로 시작 스크립트가 해당 디렉터리의 소유자를 `node`로 바꾸고 권한을 `0700`으로 설정한다. 이 짧은 준비 단계만 root로 실행한 뒤 `gosu node`로 내려가 Node 서버를 실행한다. 서버 프로세스는 root로 실행하지 않는다. 데이터 경로는 `/data`만 허용하며 기존 서버의 운영 비밀키 필수 검사를 그대로 유지한다.

`.dockerignore`는 전체를 차단한 뒤 파일 이름을 명시한 허용 목록이다. 서버 소스, 잠금 파일과 공개 화면·자산만 빌드 문맥에 들어간다. `.handoff`, `.sage`, `.git`, `.data`, `.env`, `node_modules`, 테스트 코드·계정·QA 비밀번호, 문서와 배포 설정은 이미지에 복사하지 않는다. 새 공개 자산을 추가할 때는 이 허용 목록도 함께 검토해야 한다. [Docker 빌드 문맥과 제외 파일](https://docs.docker.com/build/concepts/context/)

| 실행 환경 변수 | 설정 위치 |
| --- | --- |
| `NODE_ENV=production` | `fly.toml` |
| `HOST=0.0.0.0`, `PORT=8766`, `DATA_DIR=/data` | `fly.toml` |
| `BETTER_AUTH_URL` | 단계별 정식 HTTPS 출처, `fly.toml` |
| `BETTER_AUTH_SECRET` | 사용자가 준비한 32자 이상 전용 값, Fly의 운영 secret |

비밀키의 실제 값은 이 문서·명령 기록·저장소에 적지 않는다. 기존 게임의 비밀키를 복사하지 않는다. 사용자가 신뢰하는 방법으로 직접 발급·설정하며, CLI를 이용한다면 비밀값을 인자에 쓰는 방식 대신 보호된 외부 파일을 표준 입력으로 받는 `fly secrets import`를 사용한다. 적용 앱을 반드시 새 전용 앱으로 지정한다. [Fly secret 안내](https://docs.fly.io/apps/secrets), [표준 입력 명령](https://docs.fly.io/flyctl/cmd/fly_secrets)

운영 비밀키가 없거나 `BETTER_AUTH_URL`이 없거나 HTTPS가 아니면 서버는 시작에 실패한다. 이 조건을 우회하거나 개발용 비밀키를 운영에 재사용하지 않는다. 이메일 인증·비밀번호 복구 메일은 아직 연결하지 않았다.

## 기본안: 전체 사이트를 같은 출처로 이전

기존 Node 서버는 `/`, `/games/…`, `/community/…`, `/api/…`를 모두 제공한다. 전체 사이트를 이전하면 게임 홈페이지의 기존 상대 경로와 커뮤니티 API 호출을 그대로 쓸 수 있다.

1. 비용과 운영 비밀키에 관한 사용자 단계가 끝나면, 새 앱의 `https://gracekin-games-community.fly.dev`에서 전체 사이트를 먼저 검증한다. 준비된 `fly.toml`의 `BETTER_AUTH_URL`과 상태 확인 `Host`는 모두 이 주소다.
2. 두 계정으로 가입·로그인, 게시글·댓글의 공유·수정·삭제·권한, 서버 재시작 후 지속성을 확인한다. 대문→게임 홈페이지→START, 공식 안내와 비공개 경로 차단도 확인한다. 실제 공개 가입을 받기 전에 커뮤니티에서 연결하는 개인정보처리방침이 이번 계정·글·댓글 처리를 포함하는지 확인한다. 이 문서에서는 방침 내용을 추정해 새로 작성하지 않는다.
3. 사용자 도메인 연결 단계에서 `gracekingames.com` 인증서와 DNS 전환을 준비한다. Fly가 해당 앱에 안내하는 주소를 사용하며 IP를 추정해 적지 않는다. **슬라임·경국지계 하위 도메인, 메일 MX·SPF/TXT와 기존 인증용 DNS는 보존한다.** [Fly 사용자 도메인 안내](https://docs.fly.io/networking/custom-domain/)
4. 전환 시 `BETTER_AUTH_URL`을 `https://gracekingames.com`으로, 상태 확인 `Host`를 `gracekingames.com`으로 함께 바꾸어 배포한다. 이후 Fly 기본 주소는 현재 서버의 Host 검사에서 `403`이 된다. 인증 쿠키 출처도 달라지므로 기본 주소에서 만든 세션은 정식 도메인에 이어지지 않으며 재로그인이 필요하다.
5. 현재 서버는 **한 Host만 허용**한다. `www.gracekingames.com`을 단순히 같은 Fly 앱에 연결하면 `403`이므로 `www`→루트의 정식 리다이렉트를 먼저 준비하고 검증해야 한다. 그 전에는 `www` DNS를 임의 전환하지 않는다. 기존 Pages의 `www` 리다이렉트를 유지할 경우 실제 동작과 유지 조건을 확인한다.
6. DNS가 전파된 뒤 루트에서 다시 전체 흐름을 확인한다. 기존 Pages의 `/community/` 주소는 같은 `gracekingames.com` 주소가 새 서버로 연결되므로 URL을 바꾸지 않고 이전된다. Pages 배포와 `CNAME`은 전환 직후 바로 삭제하지 않아 원복 경로를 남긴다.

단일 Host를 유지하는 동안 위 두 주소를 동시에 정상 운영하는 것으로 설명하지 않는다. 전환 전 DNS와 설정을 보관하고, 원복하면 새 회원 데이터는 Pages에서 사용할 수 없다는 점을 함께 기록한다. 기존 볼륨은 삭제하지 않는다.

## 대안: 커뮤니티만 별도 주소로 운영

`community.gracekingames.com` 또는 Fly 기본 주소에서 커뮤니티 HTML과 API를 함께 제공할 수도 있다. 대문·게임 홈페이지는 Pages에 남아 영향을 적게 받지만, 게임 홈페이지의 커뮤니티 링크와 기존 Pages `/community/`의 이동 안내를 별도로 바꿔야 한다. `/api`만 별도 서버로 보내는 구성은 현재 프런트와 인증 출처 설정에 맞지 않는다.

이 경우 `BETTER_AUTH_URL`과 상태 확인 `Host`는 선택한 커뮤니티 주소 하나로 일치시킨다. 현재 `/` 링크는 별도 서버에 함께 복사된 대문을 열고 `/games/…`도 그 서버의 복사본을 연다. 원래 Pages 대문으로 돌아가는 것으로 오해하지 않도록 실제 URL·탐색 동선을 검토한 뒤 공개 링크를 전환한다. 이번 준비에서는 링크나 DNS를 수정하지 않았다.

## 사용자 단계 이후의 예정 명령

다음은 **아직 실행하지 않은** 새 자원 생성·배포 절차다. 조직·이름·비용과 사용자 운영 비밀키 설정이 준비된 뒤 조율자가 대상과 순서를 다시 확인한다. 기존 앱 이름으로 치환하지 않는다.

```sh
fly apps create gracekin-games-community --org <선택한-조직>
fly volumes create community_data --app gracekin-games-community --region nrt --size 1 --count 1
```

앱 생성과 볼륨 생성은 [공식 앱 명령](https://docs.fly.io/flyctl/cmd/fly_apps_create), [공식 볼륨 명령](https://docs.fly.io/flyctl/cmd/fly_volumes_create)에 맞춘다. 사용자가 전용 운영 비밀키를 설정하고 실제 값이 아닌 secret 이름만 확인한 뒤 진행한다.

```sh
fly config validate --strict --config fly.toml
fly deploy --app gracekin-games-community --config fly.toml --ha=false
fly status --app gracekin-games-community
fly volumes list --app gracekin-games-community
fly checks list --app gracekin-games-community
```

상태 확인은 내부 HTTP 요청이므로 설정의 `Host` 헤더가 중요하다. Fly의 외부 HTTPS 강제 설정과 별개로 현재 서버는 HTTP 자체를 리다이렉트하지 않아 이 검사에서 `200`을 반환할 수 있다. 실제 배포에서는 검사 성공과 Machine 1개·볼륨 1개 연결을 확인한다.

## 이번 준비의 검증 기록

- Node.js `v24.20.0`에서 `npm ci --omit=dev --ignore-scripts`와 기존 `npm test`: 14개 통과.
- `/Users/app/.fly/bin/flyctl config validate --strict --config fly.toml`: 통과. 앱 생성이나 배포는 수행하지 않았다.
- 공식 Docker Hub에서 고정 이미지 태그 존재 확인.
- Docker CLI가 PATH와 `/Applications/Docker.app/Contents/Resources/bin/docker`에 없어 이미지 빌드·컨테이너 실행은 수행하지 못했다. 따라서 실제 컨테이너 UID, 새 볼륨 소유권, Linux 이미지 기동과 Fly 상태 확인은 배포 전 확인해야 한다.
- 허용 파일 목록과 Docker 복사 경로를 정적으로 대조하고 비밀정보 패턴·문서 공백 검사를 수행한다. 실제 Docker 문맥 검사와 동일한 검증이라고 주장하지 않는다.
