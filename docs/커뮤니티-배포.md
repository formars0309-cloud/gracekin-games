# 커뮤니티·공통 계정 서버 배포 기록

2026-10-16 회원 커뮤니티의 정식 출처를 `https://community.gracekingames.com`으로 전환하는 배포를 완료했다. 이전 운영 주소는 `https://gracekin-games-community.fly.dev`였으며, 옛 Host의 GET·HEAD 화면 요청은 새 출처로 301 이동하고 API·쓰기 요청은 403으로 거부한다. 전용 Fly 앱 `gracekin-games-community`는 유지한다. 같은 날 사용자의 공개 배포 요청에 따라 공통 계정 서버와 Pages를 배포했다. 최초 공통 계정 배포에서는 운영 메일을 연결하지 않아 신규 가입·메일·보호자 신청이 준비 중이었다. 이후 Resend 일반 메일과 보호자 회신 자동 동의를 순서대로 개방했다. 이후 그레인 가입 보상과 지갑을 Fly·GitHub Pages에 공개했으며, 공개 설정·모바일 화면·Pages 반영과 내부 파일 비공개를 확인했다. 기존 계정 로그인과 공개 글 읽기는 유지한다.

대문과 게임 홈페이지는 `https://gracekingames.com`의 GitHub Pages에 둔다. Fly 앱 이름, 영속 데이터 경로와 기존 회원·글·댓글 데이터는 유지한다. 도메인 전환에 이어 공통 계정 기능을 배포했으며, 메일 설정과 보호자 절차는 [공통 계정 운영 문서](공통계정-운영.md)를 따른다. 기존 경국지계 앱과 그 비밀키·볼륨은 사용하지 않는다.

## 배포 준비

커뮤니티 개편 2단계는 서버·DB 구현만 준비한 상태다. 이 작업에서는 운영 Fly·운영 DB에 접속하지 않았으며 푸시·배포하지 않았다. 아래는 조율자가 별도 공개 배포 요청을 받은 뒤 실행할 절차다. API와 대표 그림 키는 [2단계 API 계약](기획/커뮤니티-벤치마킹.md#2단계-api-계약)을 따른다.

1. **운영 DB 백업.** 기존 단일 Machine·볼륨을 유지하고 쓰기와 보상 타이머를 중지할 점검 시간을 잡는다. SQLite 온라인 백업 API 또는 `sqlite3`의 `.backup`으로 일관된 별도 백업을 만들고 운영 볼륨 밖의 접근 제한 보관처에도 보존한다. 실행 중인 WAL DB의 본체 파일만 복사하지 않는다. 백업 사본의 `PRAGMA integrity_check`가 `ok`, `PRAGMA foreign_key_check`가 빈 결과인지 확인하고 이전 서버 이미지·소스와 복구 경로를 기록한다. 비밀정보·회원 데이터·백업 파일은 저장소에 넣지 않는다.
2. **백업 사본에서 이전 연습.** 새 코드의 `initializeCommunitySchema(db)`를 아래처럼 사본에 두 번 실행한다. 옛 CHECK 제약을 가진 `community_posts`를 `BEGIN IMMEDIATE` 안에서 새 테이블로 복사하고 교체한다. 기존 열·글 rowid를 보존하며 새 `category`, `cover`, `status`는 `null`이다. 외래키를 트랜잭션 시작 전 잠시 끄고 댓글·감사 연쇄 삭제를 방지한다. 글 인덱스·트리거 SQL을 복원하고 전체 `foreign_key_check`를 통과해야 커밋한다. 실패하면 스키마와 데이터 모두 롤백하고 기존 외래키 설정도 복원한다. 이미 이전된 테이블은 재생성하지 않는다.
3. **보존·기동 확인.** 사본의 글·댓글·신고·보상·원장·감사 기존 열 내용과 행 수, 외래키, 인덱스·보상 트리거를 이전 전과 대조한다. 신규 시험 `test/community-phase2.test.js`는 옛 스키마 자료 보존·두 번 실행·실패 시 롤백·이전 후 숨김/삭제 연쇄 동작을 검증한다. 배포 시 서버는 요청 수신과 보상 타이머 시작 전에 같은 이전을 자동 실행한다. 점검 중 운영의 새 열·CHECK 제약, 무결성·외래키, 기존 기록 보존과 재기동을 확인하고 승인된 검증 범위에서 권한·신고·숨김을 확인한다. 두 게임 화면 연결은 별도 검수 후 공개한다.
4. **롤백.** 이전 도중 실패하면 자동 트랜잭션 롤백 후 서버 시작이 실패하므로, 원인을 확인하고 이전 이미지로 되돌린다. 커밋 후 문제가 발견되면 쓰기·타이머를 중지하고 현재 DB와 WAL/SHM까지 별도 보존한다. 점검 시작 때 만든 백업을 이전 서버 이미지와 함께 복원하고, 실패 DB의 WAL/SHM은 보존처로 이동하여 복원 DB에 재적용되지 않게 한다. 무결성·외래키·기록을 확인한 뒤 기동한다. 새 `notice`를 옛 CHECK 제약 테이블에 넣는 역이전은 제공하지 않는다. 운영 쓰기를 다시 연 뒤의 백업 복원은 그 뒤 변경을 잃으므로 자동 수행하지 않고 후속 변경을 먼저 보존·대조한다.

아래 명령은 **운영 파일이 아닌 로컬 백업 사본**에만 실행한다. 실행 환경의 경로를 명시해야 하며 서버와 같은 DB 연결을 공유하거나 실행 중인 서버에 붙여 사용하지 않는다.

```sh
COMMUNITY_DB_COPY=/절대경로/로컬-백업-사본.sqlite node --input-type=module <<'JS'
import { DatabaseSync } from 'node:sqlite';
import { statSync } from 'node:fs';
import { initializeCommunitySchema } from './server/community.js';
const path = process.env.COMMUNITY_DB_COPY;
if (!path || !statSync(path).isFile()) throw new Error('기존 로컬 백업 사본을 지정해 주세요.');
const db = new DatabaseSync(path);
try {
  db.exec('PRAGMA foreign_keys=ON; PRAGMA busy_timeout=5000;');
  initializeCommunitySchema(db);
  initializeCommunitySchema(db);
  console.log(db.prepare('PRAGMA integrity_check').all());
  console.log(db.prepare('PRAGMA foreign_key_check').all());
} finally { db.close(); }
JS
```

## Resend 연결과 공개 활성화 (2026-10-16)

`mail.gracekingames.com`의 인증을 마친 Resend를 연결했다. 발신은 `account@mail.gracekingames.com`, SMTP는 `smtp.resend.com:465`·사용자 `resend`, 발송 리전은 도쿄다. Resend의 미국 저장·처리, ImprovMX의 프랑스·미국 수신·전달, Google Gmail의 운영자 수신함 처리를 공개 방침과 동의문 버전 `2026-10-16-v2`에 반영했다.

연결 전 SMTP TLS 인증과 실제 2통의 Gmail 도착, `support@gracekingames.com`의 ImprovMX 전달, SPF·DKIM 통과를 확인했다. 이어 실제 SMTP를 사용한 격리 DB 통합시험 24항목과 인증·복구·보호자 안내 메일 3통의 도착을 검증했다. 실제 보호자 회신·수동 승인은 시험하지 않았다.

일반 메일 활성화 당시 공개 서버에는 SMTP 설정 5개만 비공개 표준 입력으로 적용했다. `/api/account/config`에서 메일·가입 `true`, 보호자 동의 `false`를 확인했다. `GUARDIAN_REPLY_TO`를 등록하지 않아 당시 어린이 신청은 닫혀 있었다. 이 단계에서는 운영 DB에 시험 회원·보호자 신청을 만들지 않았다. 이후 사용자가 요청한 회신 자동 확인은 아래 별도 단계로 기록한다.

## 보호자 회신 자동 확인 연결·개방 절차 (2026-10-16)

사용자의 요청에 따라 보호자 회신을 정해진 조건으로 자동 확인하는 서버·화면을 `176755d`로 통합했다. 일반 가입·인증·복구를 유지하면서 자동 수신 검증과 개방을 단계별로 진행한다. 아래는 연결·개방 절차이며 실제 완료 결과는 검증 이력에 구분해 기록한다.

연결 시 `GUARDIAN_CONSENT_MODE=email-reply-auto`, 실제 Resend 수신 주소인 `GUARDIAN_REPLY_TO`, `RESEND_RECEIVING_API_KEY`, `RESEND_WEBHOOK_SECRET`를 사용한다. 수신 알림 경로는 `/api/webhooks/resend/guardian`이며 Resend의 `email.received` 이벤트를 등록한다. 먼저 `GUARDIAN_AUTO_APPROVAL_READY=false`에서 실제 수신의 서명·고정 API 조회·발신 인증·주소·메타데이터를 검증한다. 이 상태는 신청 접수와 기존 신청의 승인·보류 변경을 막고 개인정보 없는 `readiness_verified` 이벤트만 기록한다. `DATA_DIR=/data node scripts/guardian-review.mjs readiness`의 확인 건수·최근 시각을 실제 시험과 대조한다. 실제 연결과 별도 환경의 정확한 동의 승인·부적합 회신 보류·증빙 시험을 검수하고 공개 개방을 결정한 뒤에만 `GUARDIAN_AUTO_APPROVAL_READY=true`를 설정한다. 기존 SMTP 발송 전용 키는 유지하며 수신 조회용 Full access 키·서명키의 신규 발급은 사용자에게 맡긴다.

Resend 기본 수신 주소를 쓰면 DNS를 추가하지 않아도 된다. 자체 수신 하위 도메인을 쓰더라도 루트 도메인의 ImprovMX 수신 MX는 보존한다. 문의·철회는 기존 지원 메일로 받고 자동 동의 회신은 별도 Resend 주소로 받는다. 실제 수신 주소·키와 원문은 배포 기록에 넣지 않는다.

활성화 전 공개 방침·서버 동의문 v3·계정 화면의 자동/수동 안내를 통합 검수하고 기존 DB·증빙을 백업한다. 수신 권한, 웹훅 서명, 서버에서 조회한 권위 있는 인증 결과, 다른 주소·코드·버전 및 인용문 회신 거부, 일반 텍스트와 HTML 내용 상충·숨김·복잡한 HTML 보류, 한 번 승인과 증빙 정리를 확인한다. 실제 수신 연결 시험과 별도 환경의 판정·가입·삭제 시험을 구분해 기록한다. 화면은 `reviewStatus=held`를 승인으로 다루지 않고 이유와 재회신·문의 방법을 표시해야 한다. 검증 전에는 운영의 `guardianConsentAvailable=false`와 준비 중 화면을 유지한다.

## 현재 설정

| 항목 | 설정값 | 확인할 점 |
| --- | --- | --- |
| 전용 앱 | `gracekin-games-community` | 운영 중인 앱을 유지하며 새 앱을 생성하지 않는다. |
| 정식 출처 | `BETTER_AUTH_URL=https://community.gracekingames.com` | 인증 API·세션 쿠키·화면의 출처를 하나로 맞춘다. |
| 이전 주소 | `LEGACY_HOSTS=gracekin-games-community.fly.dev` | 정확히 일치하는 Host의 GET·HEAD 화면 요청만 301 이동한다. |
| 상태 확인 | `GET /health`, `Host: community.gracekingames.com` | 30초 간격·5초 제한·시작 유예 30초. DB·인증·API 제한과 분리된 최소 응답이다. |
| 지역·Machine | `nrt`, `shared-cpu-1x`, 메모리 512MB, 1개 | 기존 설정을 유지한다. 최초 준비에서 256MB보다 여유 있게 잡은 값이며 실부하 측정값은 아니다. |
| 영속 볼륨 | `community_data`, `/data` | 2026-10-16 공통 계정 배포에서 기존 1GB 볼륨을 유지했다. `/data/community.sqlite`와 SQLite 부속 파일을 보존한다. |
| 유휴 상태 | 자동 정지·자동 시작, 최소 실행 0개 | 다음 방문에 초기 응답 지연이 생길 수 있다. |
| 동시 요청·배포 | 권장 한도 10, 최대 20, rolling, 한 번에 1개 중단 | 단일 SQLite 서버이므로 배포 중 잠시 중단될 수 있다. |

`HOST=0.0.0.0`, `PORT=8766`, `DATA_DIR=/data`, `NODE_ENV=production`은 `fly.toml`에 유지한다. `TRUST_FLY_PROXY=true`는 `FLY_APP_NAME`이 정확히 전용 앱과 일치할 때만 Fly Proxy의 접속자 IP를 신뢰한다. `BETTER_AUTH_SECRET`은 32자 이상인 기존 전용 운영 secret을 유지하며 실제 값을 문서·로그·저장소에 적지 않는다. 운영 비밀키가 없거나 정식 출처가 없거나 HTTPS가 아니면 서버는 시작에 실패한다. 개발용 비밀키를 운영에 재사용하지 않는다.

실행 시간, 볼륨, 전송량에는 비용이 발생한다. 이 문서의 자원 설명은 신규 비용을 승인하거나 자원 생성을 지시하는 것이 아니다. 자원 변경이 필요하면 조율자가 승인 범위와 현재 상태를 확인하고 [공식 요금 계산기](https://fly.io/calculator/)로 예상 비용을 검토한다. 최초 준비 당시 금액은 확정하지 않았다.

자동 시작·정지, 동시 요청 한도와 상태 확인 헤더는 [Fly 설정 문서](https://docs.fly.io/reference/configuration)를 따른다. 최초 배포 때 검토했던 `--ha=false`는 추가 Machine 생성을 막기 위한 옵션이며 Machine 수를 설정 파일만으로 고정하지 않는다. 기존 운영 앱의 Machine 수를 먼저 확인하고 도메인 전환을 이유로 새 앱이나 볼륨을 만들지 않는다. [Fly 배포 명령](https://docs.fly.io/flyctl/cmd/fly_deploy)

## 주소와 요청 호환

- Pages의 `/community/`에 들어오면 `assets/community/host.js`가 새 정식 출처로 이동한다. 경로·쿼리·해시를 보존하며, 정확히 `gracekingames.com`과 `www.gracekingames.com`에서만 실행한다. 이동 중 회원 화면 초기화를 종료하므로 Pages에 회원 API 요청을 보내지 않는다. 자바스크립트를 끈 경우 안내 링크도 새 출처를 가리킨다.
- 옛 Fly 기본 Host는 서버의 `legacyHosts` 옵션 또는 `LEGACY_HOSTS` 환경 변수에 명시했을 때만 호환한다. 운영에서는 `fly.toml`로 지정한다. 실제 요청 Host가 정확히 일치한 GET·HEAD 요청만 같은 경로·쿼리의 고정 정식 출처로 301 이동한다. `/health`도 옛 주소에서는 301이며, 상태 확인은 새 Host로 보낸다. `/account/`와 메일 링크의 계정 경로도 같은 규칙을 따른다. URL 해시는 HTTP 요청에 포함되지 않으므로 서버가 읽거나 조합하지 않는다. 301의 Location에 해시가 없으면 브라우저가 원래 해시를 유지하므로 옛 주소로 받은 `#token=...`도 새 화면에 전달된다.
- 옛 Host의 `/api`와 `/api/…`, 그 외 메서드는 403으로 거부한다. 새 출처의 Origin을 붙이거나 쿠키를 보내도 옛 Host에서 세션·쓰기 API를 사용할 수 없다. 임의 Host, 유사한 이름, 포트가 붙은 옛 Host도 403이다. 목적지 출처는 사용자 입력이나 전달 헤더로 바꿀 수 없다.
- 새 Host에서는 화면과 API가 같은 출처로 동작한다. 새 Host의 계정·게시판 쓰기 요청도 새 출처의 Origin을 요구한다. 쿼리가 없는 보호자 수신 웹훅 POST는 Origin 검사 대신 Resend 서명을 확인하는 예외이며 기존 계정 API의 출처 검사를 완화하지 않는다. 커뮤니티의 로고·게임 홈페이지 복귀 링크는 `https://gracekingames.com/`과 `/games/…/`로 연결하고 로컬 개발에서는 상대 경로를 유지한다.
- 도메인이 바뀌면 브라우저의 기존 로그인 세션은 이어지지 않으므로 한 번 다시 로그인해야 한다. 서버에 저장된 계정·글·댓글은 그대로 사용한다. 공통 계정의 이메일 인증·비밀번호 복구·보호자 동의 메일과 링크·콜백은 `BETTER_AUTH_URL`의 새 출처를 기준으로 만든다. 만 14세 미만은 보호자 회신 자동 확인으로 승인된 뒤 같은 신청 브라우저에서 한 번 가입한다.

## 도메인 전환 확인 절차

도메인 전환은 2026-10-16 배포 완료했다. 아래는 전환 때 사용할 확인 절차를 보존한 것이며, DNS·인증서 전환이 아직 남아 있다는 뜻이 아니다. 이후 공통 계정 배포에서도 새 출처·기존 데이터·이전 Host 호환을 다시 확인했다. 실제 검증 결과는 아래 공통 계정 공개 배포 기록에 따로 적었다. 새 주소가 준비되기 전에 목적지를 공개하면 접근 불가가 될 수 있으므로, 이후 주소 변경에도 기존 운영 상태와 원복 방법을 확인하고 전환 시점을 맞춘다.

1. 기존 앱·Machine·볼륨·비밀키 설정과 SQLite 백업·복구 경로를 확인한다. 기존 자원을 중복 생성하지 않는다.
2. `community.gracekingames.com`의 Fly 사용자 도메인 인증서와 DNS를 준비하고 HTTPS 사용 가능 여부를 확인한다. 루트·`www`·게임 하위 도메인·메일 MX·SPF/TXT는 보존한다.
3. 새 출처·이전 허용 Host·상태 확인 Host를 포함한 서버 변경을 배포한다. 새 Host의 `/health`가 200인지 확인한다. 정식 출처에 맞는 Host가 없는 내부 검사는 403이므로 설정 헤더를 함께 적용한다.
4. 새 주소에서 두 계정의 가입·로그인, 글·댓글 공유·수정·삭제·권한과 재시작 후 지속성을 확인한다. 기존 로그인 사용자는 다시 로그인한다.
5. 옛 주소의 GET·HEAD가 경로·쿼리를 보존한 301인지, 옛 API·쓰기와 임의 Host가 403인지 확인한다. Pages의 이동 목적지·경로·쿼리·해시와 새 주소의 복귀 링크·개인정보처리방침도 확인한다.
6. 서버의 새 주소가 정상 응답하는 시점에 Pages 변경을 공개하고 최종 공개 검증 결과를 기록한다. 이전 데이터·볼륨·호환 주소를 바로 삭제하지 않는다.
