# 회원 아바타 공방

## 한 회원이 여러 게임에서 같은 캐릭터를 쓰는 흐름

대문의 **캐릭터 만들기**를 누르면 `/games/avatar/`가 열린다. 손님도 외형과 직업을 고르고 초상화·보드 말·탐험 캐릭터로 확인할 수 있다. 새 창에서 로그인한 뒤 공방으로 돌아와 **손님 초안 가져오기**, **계정에 저장**을 누르면 내 계정에 이름·직업·초상이 표시된다. 회원이 이름·외형·직업을 바꿔도 저장된 아바타 ID는 유지된다.

| 사용자의 행동 | 화면·서버의 처리 | 확인할 결과 |
| --- | --- | --- |
| 처음 공방에 들어온다 | 세션으로 내 아바타를 조회한다. 저장 기록이 비어 있으면 기본 캐릭터를 편집기에 넣는다. | 첫 방문만으로 저장 기록을 만들지 않는다. |
| 얼굴·체형·색을 바꾸고 돌려 본다 | 편집 중인 캐릭터를 렌더러에 전달한다. 얼굴과 전신을 오가고 제자리·걷기를 선택한다. | 보기를 바꿔도 입력값이 유지된다. |
| 직업 추천을 확인하고 직업을 고른다 | 추천 결과와 실제 선택을 별도 필드에 둔다. | 다른 직업을 골라도 추천 결과와 최종 선택이 각각 복원된다. |
| 계정에 저장하고 다시 방문한다 | 처음에는 버전 0, 이후에는 마지막 조회·저장 응답의 버전으로 저장한다. 서버가 확정한 결과를 화면에 반영한다. | 같은 계정으로 다시 로그인하면 마지막 저장 상태가 보인다. |
| 게임에서 쓸 파일을 받는다 | **게임 파일 만들기**를 누르고 **게임 파일 받기 (ZIP)**로 내려받는다. | 투명 초상과 말, 네 방향 보행 시트, 좌표표, 현재 외형과 직업을 받는다. |

## 모델과 소유권

기본값과 입력 검사의 기준은 `assets/avatar/model.js`다. `createAvatarPreset('youth')`는 미소년, `createAvatarPreset('maiden')`은 미소녀 캐릭터를 새로 만든다. `createDefaultCharacter()`는 미소년 프리셋과 같은 값으로 시작한다. 두 프리셋은 턱선, 눈과 코의 비율, 어깨와 체격, 머리 모양과 배색을 각각 조합한다. 매번 새 캐릭터와 외형 객체를 돌려주므로 한 캐릭터를 편집한 뒤에도 원래 프리셋을 다시 고를 수 있다.

두 외형 모두 처음에는 수호기사이고 추천 직업은 비어 있다. 직업 선택지는 `JOBS`의 `{id,label}`을 사용한다. 편집 중 프리셋을 바꿀 때는 새 프리셋의 `appearance`만 적용해 사용자가 정한 이름·직업·추천 결과를 유지한다. 저장할 때는 최종 외형값을 담으므로 이후 기본 디자인을 바꾸더라도 회원이 저장한 모습은 그대로 복원된다.

| 필드 | 허용값과 의미 |
| --- | --- |
| `name` | 게임 안에서 쓰는 이름. 앞뒤 공백을 정리한 뒤 유니코드 코드 포인트 1~24자. 한 줄 일반 텍스트로 표시한다. |
| `appearance.height, build, shoulders` | 키·체격·어깨를 조절하는 0~100 정수. |
| `appearance.jaw, eyes, nose` | 턱·눈·코를 조절하는 0~100 정수. |
| `appearance.hairStyle` | 머리 모양을 고르는 0~3 정수. |
| `appearance.skinColor, hairColor, eyeColor, clothColor` | 피부·머리·홍채·옷에 적용하는 소문자 여섯 자리 `#rrggbb`. |
| `job` | 최종 직업. `guardian` 수호기사, `ranger` 숲길잡이, `arcanist` 룬술사, `healer` 별빛치유사. |
| `recommendedJob` | 추천 직업 ID. 아직 추천을 받지 않았으면 `null`. |

SQLite의 `avatars`는 회원마다 한 행을 둔다. 첫 저장 때 서버에서 별도 UUID를 발급한다. 소유자는 기존 공통 계정의 `user.id`로 연결하고, 계정 삭제 시 외래 키의 `ON DELETE CASCADE`로 해당 아바타도 함께 삭제한다. 공방 도입 전 가입한 회원은 첫 저장 때 같은 절차를 거친다. 로그인·보호자 동의 상태 확인은 기존 계정 서비스를 따른다.

## 저장과 재시도

인증 서버와 같은 출처에서 세션 쿠키를 포함해 요청한다. 운영 게임 주소는 `https://community.gracekingames.com/games/avatar/`다. 정적 사이트에서 계정 기능을 쓰려면 이 주소로 이동한다.

| 요청 | 서버의 결과 |
| --- | --- |
| `GET /api/avatar/me` | 최초에는 200 및 `{"avatar":null}`. 저장 후에는 200 및 `{avatar:{id,revision,character}}`. |
| `PUT /api/avatar/me` | JSON 본문은 `{revision,character}`. 최초 생성 요청은 0, 응답 버전은 1이다. 수정에 성공하면 버전이 1 증가하고 같은 ID와 확정된 캐릭터를 반환한다. |
| 읽기·쓰기에 유효 세션이 없음 | 401. 입력 중인 캐릭터를 저장 완료로 표시하지 않는다. 다시 로그인하면 현재 회원의 기록부터 확인한다. |
| 버전이 다르거나 다른 탭에서 먼저 생성 | 409. 최신 상태를 조회해 차이를 알리고 사용자가 다시 저장할 때 최신 버전을 쓴다. |
| 조회·저장 직전 로그인 계정이 바뀜 | 공방이 세션에서 확인한 아이디를 `X-Avatar-Owner`에 담는다. 서버가 현재 로그인 계정과 비교해 다르면 412를 반환하고, 공방은 현재 계정의 기록을 다시 불러온다. 헤더를 생략한 기존 소비자는 자신의 세션으로 조회·저장한다. |
| 저장 응답을 받기 전 연결 끊김 | 재접속해 GET으로 버전과 캐릭터 값을 확인한다. 이미 반영됐다면 그 응답을 채택하고, 다른 변경이 있으면 충돌 처리로 돌아간다. |
| 잘못된 범위·타입·필드, 지나치게 큰 본문 | 422 또는 413. 행과 버전을 유지한다. 잘못된 JSON은 400, JSON이 아닌 쓰기는 415다. |

같은 버전의 동시 쓰기는 생성 시 소유자 유일 제약, 수정 시 소유자와 버전을 함께 검사하는 단일 SQL문으로 판정한다. 서버는 인증 세션에서 대상 레코드를 선택한다. 반환 객체에는 아바타 ID·버전·게임 캐릭터만 담긴다. 동일 출처의 후속 게임은 이 조회를 그대로 사용할 수 있다. 다른 출처의 게임은 내려받은 게임 파일을 사용할 수 있다.

## 게임에서 그리는 계약

`/assets/avatar/renderer.js`의 `createAvatarView(container, character, {mode = 'studio'} = {})`는 동기적으로 보기를 만든다. 공방은 `studio`, 게임 말은 `board`, 역할수행 게임은 `rpg`, 인물 사진은 `portrait`를 쓴다. 소비자는 `update(character)`로 변경을 반영하고 `setView('full'|'face')`, `rotate(deltaRadians)`, `setMotion('idle'|'walk')`로 카메라와 움직임을 조작한다. 화면을 떠날 때 `dispose()`로 보기를 정리한다.

예를 들어 같은 출처의 보드 게임은 아래처럼 현재 말의 ID와 보기를 얻는다. 호출자는 빈 결과를 받으면 공방으로 연결하고, 다음 방문에는 서버의 최신 값을 다시 읽는다.

```js
import { createAvatarView } from '/assets/avatar/renderer.js';

async function loadBoardPiece(container) {
  const response = await fetch('/api/avatar/me', { credentials: 'same-origin' });
  if (response.status === 401) throw new Error('로그인 후 내 말을 불러올 수 있습니다.');
  if (!response.ok) throw new Error('아바타를 불러오지 못했습니다.');
  const { avatar } = await response.json();
  if (!avatar) return null;
  return { id: avatar.id, view: createAvatarView(container, avatar.character, { mode: 'board' }) };
}
```

## 검증 기준

- HTTP 통합 시험에서 실제 신규 가입·메일 확인·로그인 후 빈 상태, 첫 저장, 수정, 재조회, 서버 재시작 후 동일 ID와 데이터를 확인한다.
- 같은 이름을 쓰는 두 계정에서 각각 자신의 기록만 읽고 수정하는지, 과거 버전의 수정과 중복 생성이 409인지 확인한다. 탈퇴 처리 후 기존 쿠키 접근과 잔존 행도 검사한다.
- 모든 외형값의 경계·형식, 필수 필드와 직업 ID를 검사한다. 입력 오류나 동시 편집으로 기존 데이터가 손상되지 않아야 한다.
- 통합 화면 검수 시 작은 휴대전화 폭과 키보드만으로 이름·외형·직업·저장을 조작한다. 입력마다 한국어 레이블을 확인하고 저장 결과와 충돌을 보조기술에서도 알 수 있어야 한다.
- 네 보기에서 외형 필드를 하나씩 바꿔 실제 반영을 확인하고 얼굴 확대·전신·회전·걷기를 점검한다. 운영 패키지에는 게임 진입 HTML, 브라우저 모듈과 렌더 자산, 서버 모듈이 모두 필요하다.

통합 화면, 두 계정의 실제 저장·복구, 게임 파일과 이동 검수의 실행 결과는 [공방 통합 검증 기록](../../reports/2026-11-19-아바타-통합/검증.md)에 있다.
