# 캐릭터 서버 구현 보고

- 날짜: 2026-11-19
- 브랜치: `formars0309-cloud/character-server`
- 정본: `docs/기획/캐릭터-구현-계약.md`
- 상태: 조율자 서버 구현 승인. 허가된 기존 시험 기대값 한 줄 수정을 완료했고, **전체 시험 215개 모두 통과**했다. 이전에 통과한 공통 검증을 포함해 서버 작업 완료 기준을 충족했다.
- 작업은 현재 워크트리에서 직접 수행했다. 재위임·하위 워크트리 생성·운영 API/DB 접근·공개 배포·main 푸시는 하지 않았다.

## 구현 내용

- `assets/character/model.js`: 외부 의존성 없는 순수 ES 모듈. 계약의 내보내기 17개, 스탯 10종·종족 10종·직업 10종·2차 갈래 20종·외형 ID·고정 피부·레벨·포인트·칭호·전직 조건을 구현했다. 선택지 상수는 하위 객체까지 동결하며 기본 캐릭터는 호출마다 새 객체를 만든다.
- `server/character/index.js`: 회원당 캐릭터 한 개, UUID·revision·외형·분배·누적 경험치·초기화 기록과 경험치 원장을 기존 SQLite DB에 저장한다. 두 테이블의 회원 외래키에 `ON DELETE CASCADE`를 적용했다.
- 내 캐릭터 조회·생성·수정·분배·초기화·출석 API를 구현했다. 모든 쓰기는 `BEGIN IMMEDIATE` 안에서 현재 revision과 상태를 다시 확인한다. 경험치 지급도 revision을 올리므로 오래된 화면에서 저장하면 409로 최신 상태를 다시 읽도록 한다.
- 경험치의 양·출처·날짜는 서버만 정한다. eventId 중복, 한국시간 출처별 하루 횟수, 하루 합계 300, 보상 정지 계정, 캐릭터 없는 계정을 검사한다. 현행 세 출처의 하루 최대는 160(30+80+50)이며 합계 300 방어는 별도 경계 시험으로 검증했다.
- 그레인 출석 성공과 캐릭터 출석을 같은 트랜잭션으로 묶었다. 커뮤니티 활동이 `confirmed`로 바뀔 때 `grain:<eventId>`를 기록한다. 취소·숨김·삭제·정지된 예정 보상은 지급하지 않는다. 경험치 저장 실패는 그레인 지급·확정도 함께 롤백한다.
- 글·댓글 작성자에는 `{ race, job, level, appearance }` 또는 `null`인 `character`를 더했다. 회원 ID·이메일·캐릭터 내부 ID·원장·분배 정보는 작성자 공개 필드에 넣지 않는다. 다른 서버 모듈은 `getPublicCharacter(db, userId)`를 가져올 수 있다.
- `server/app.js`에는 모듈 생성·라우팅과 `/character/` 정적 허용만 연결했다. 기존 출처 검사·요청 제한·JSON 제한·보안 헤더 경계를 그대로 사용한다.
- Dockerfile에 `COPY character/ ./character/`, `.dockerignore`에 `character/**`, `assets/character/**`, `server/character/**`를 허용했다.

### 운영 파일 복사 시험

`test/character-package.test.js`가 실제 Dockerfile의 COPY 원본과 `.dockerignore` 규칙을 읽어 별도 임시 폴더에 운영 파일만 복사했다. 그 폴더에서 `npm ci --omit=dev --ignore-scripts --no-audit --no-fund` 후 서버를 띄웠다. 화면과 그림은 담당 작업이 아직 합쳐지지 않아 **임시 폴더에만** 자리표시 파일을 넣었다.

- `/character/`: 200
- `/assets/character/model.js`: 200, JavaScript 형식
- `/assets/character/parts/body/placeholder.webp`: 200
- `/health`: 200
- `/api/character/me`: 로그인 없이 401
- `/server/character/index.js`: 404
- 시험·보고서·`.data/community.sqlite`는 복사 대상에서 차단됨

실제 Docker 이미지 빌드·브라우저 화면 검사는 실행하지 않았다. 실제 `character/`·그림·렌더러는 타 작업자 결과를 합친 후 조율자가 검사해야 한다. 이 서버 브랜치만으로는 Docker COPY의 실제 화면 원본이 아직 없다.

## 남은 문제와 다른 담당 파일에 필요한 변경

1. **해결: `test/community-phase2.test.js:209` 기대값 수정.** 최초 전체 회귀 시험에서는 새 `character` 필드가 기존 기대값에 없어 215개 중 214개 통과·1개 실패였다. 조율자가 담당 밖 파일의 해당 한 줄 수정을 명시적으로 허가하여 아래와 같이 `character: null`을 더했다.

   ```js
   assert.deepEqual(detail.body.post.author, { name: '운영자 별명', isOperator: true, character: null });
   ```

   최초에는 임시 복사본만 수정해 해당 파일 시험 11개 통과를 확인했다. 이번에는 허가된 원본 한 줄 수정 후 `npm test` 전체를 다시 실행해 **215개 통과, 실패 0, 취소 0, 건너뜀 0**을 확인했다. 후속 변경은 이 시험 한 줄과 이 보고서 갱신뿐이며 별도 커밋으로 같은 서버 브랜치에 푸시한다.

2. 화면·그림 작업자가 계약상 담당 결과물을 합쳐야 실제 `/character/`와 그림이 생긴다. 정적 사이트에서 커뮤니티 도메인으로 쿼리를 보존하는 이동은 화면 담당이다.
3. 성인 계정 탈퇴 API는 기존 서버에 없으므로 만들지 않았다. 캐릭터·원장의 DB 외래키 연쇄 삭제를 시험했다. 기존 어린이 계정 삭제도 같은 회원 외래키 경계를 사용한다.
4. 배경 기획의 개인정보처리방침 수집 항목 검토는 서버 담당 파일 밖이다. 통합·발행 검수에서 조율자가 확인해야 한다.

## 화면 작업자에게 전달할 자료 형식

계약이 내보내기 이름만 정한 항목은 다음처럼 구체화했다. 화면에서 이 형식을 그대로 사용하면 된다.

- `STATS`: `{ id, label }[]`
- `RACES`: `{ id, label, bonus: { 스탯ID: 수치 }, fixedSkin }[]`
- `JOBS`: `{ id, label, mainStats: [스탯ID, 스탯ID], bonus, branches: [{ id, label, requirements }] }[]`
- `APPEARANCE_OPTIONS`: `{ hair: ['h1', ...], hairColor: ['c1', ...], eyeColor: [...], skin: [...], outfitColor: [...] }`. 고정 피부 종족은 별도로 `skin: null`을 사용한다.
- `EXP_RULES`: `{ attendance: { amount: 30, dailyLimit: 1 }, post: { amount: 40, dailyLimit: 2 }, comment: { amount: 10, dailyLimit: 5 }, dailyTotalLimit: 300 }`
- `titlesOf(stats)`: `{ stat, threshold, label }[]`. 충족한 모든 구간을 반환한다.
- `branchStatus(job, stats, level)`: `{ id, label, requirements, levelRequired: 15, levelMet, statsMet, exam: { games: 2, playsPerGame: 5, met: false }, available: false, message: '게임 기록 연결 뒤 열립니다' }[]`
- `reset.nextFreeAt`: 첫 사용 전 `null`, 사용 후 마지막 초기화 +30일의 ISO 문자열. `reset.available`로 현재 사용 가능 여부를 판단한다.
- 분배는 모든 스탯 ID를 키로 둔 숫자 객체이며 `progress.points`는 **남은** 포인트다.
- 경험치 원장의 `expDate`는 지급·확정한 시점의 한국 날짜다. 그레인 원장의 기존 `rewardDate` 규칙은 바꾸지 않았다.
- 출석 요청 본문은 `{}`다. revision은 쓰지 않는다. 성공/이미 출석/캐릭터 없음/보상 정지 모두 `{ granted, amount, character }`로 상태를 읽는다.
- 수정 시에는 조회한 `revision`을 전송한다. 경험치 지급도 버전을 올리므로 409가 오면 다시 조회해야 한다.

## API 예시

처음 조회(회원 로그인 필요):

```json
{ "character": null }
```

첫 생성 `PUT /api/character/me`:

```json
{ "revision": 0, "data": { "v": 1, "race": "human", "job": "guardian", "appearance": { "hair": "h1", "hairColor": "c1", "eyeColor": "e1", "skin": "s1", "outfitColor": "a1" } } }
```
